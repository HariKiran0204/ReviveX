# Recovery probability model (Phase 6)

Phase 6 estimates **P(recovery | case context, intervention)**. It does not choose the
action, execute tools, or credit `amount_recovered`. Phase 7 will consume these
probabilities inside Expected Recovery Value.

Package: `packages/eval/recoverai_eval/`

Training and inference are separate modules (`train.py` vs `inference/`).

## Dataset

Synthetic cases are generated by `recoverai_eval.data.generate`. Default size is
10,000 cases, expanded to one labeled row per closed action enum (seven actions).
Generation is deterministic given `--seed`.

Customer latent traits (payment quality, liquidity, card health, engagement, price
sensitivity) drive correlated fields. Columns are not independent noise.

Labels are Bernoulli draws from `intervention_recovery_probability` in the **existing**
local simulator (`recoverai_providers.simulator.interventions`). That function extends
`capture_probability` rather than introducing a second engine.

`CUSTOMER_CANCELLED` and `MANDATE_FAILURE` stay largely unrecoverable for automated
payment tools. `ESCALATE` and `DO_NOTHING` are scored as organic / human-assisted
recovery, not as PSP captures.

Full generation assumptions: `DATASET_ASSUMPTIONS` in
`packages/eval/recoverai_eval/data/generate.py`.

Outcome-only fields (`recovered`, `recovery_time_hours`, `true_probability`) are
never model features.

## Features

Raw domain snapshot → derived features → sklearn matrix.

Derived (no future information):

| Feature | Meaning |
| --- | --- |
| `customer_success_ratio` | Historical capture ratio |
| `recent_failure_count` | Attempt/history failure pressure |
| `communication_fatigue` | `min(1, communication_count / 8)` |
| `amount_to_clv_ratio` | Amount relative to CLV |
| `failure_action_interaction` | `failure_reason\|action` |

`action` is a first-class feature so the same case can receive different
probabilities for `RETRY_NOW`, `RETRY_LATER`, `SEND_PAYMENT_LINK`, `SEND_REMINDER`,
`OFFER_DISCOUNT`, `ESCALATE`, and `DO_NOTHING`.

Feature version: `features-v1`. Catalog: `recoverai_eval.features.engineering.FEATURE_CATALOG`.

## Target

Binary `recovered` ∈ {0, 1} for the **chosen action**. Training row = case features + action.

## Split

Customers are shuffled with the training seed and partitioned 70% / 15% / 15%
train / validation / held-out test. Every row for a customer stays in one split.
Case IDs therefore cannot leak from train into test.

## Models

Both candidates use an sklearn `Pipeline` (median/constant imputation, scaling,
one-hot encoding) plus `class_weight="balanced"`.

1. Logistic regression (baseline)
2. Random forest (same preprocessing; no extra native deps)

Each candidate is fit on train and **isotonic-calibrated** on validation
(`CalibratedClassifierCV` around a `FrozenEstimator` of the fitted pipeline). Selection uses validation Brier score.
Logistic regression wins ties within 0.003 Brier. Held-out test is not used for
selection.

## Calibration and metrics

Reported on the held-out set only:

- ROC-AUC, PR-AUC, precision, recall
- Brier score
- Calibration bins / ECE
- Confusion matrix
- Mean predicted probability vs actual recovery rate **by action**

Accuracy is not the optimization target.

## Versioning

Artifacts live under `data/ml/models/<version>/` (`model.joblib`, `metadata.json`,
`split_ids.json`). Versions increment (`recovery-v1`, `recovery-v2`, …). Existing
versions are not overwritten unless `--overwrite` is passed.

Metadata stores model version, dataset version, seed, feature version, timestamp,
algorithm, metrics, and configuration.

A production pointer (`data/ml/models/PRODUCTION`) is written only when quality
gates pass. Failed gates can still save a rejected artifact when `--no-publish`
is used; they must not become the production model.

Optional Postgres rows: `model_versions`, `model_predictions` (Alembic
`20260904_0003`). Predictions are upserted by a fingerprint of
`(merchant_id, recovery_case_id, action, model_version, feature_version)`.

## Inference API

```python
from recoverai_eval import predict_recovery_probability

result = predict_recovery_probability(case_context, action)
# result.probability ∈ [0.0, 1.0]
# result.model_version, result.feature_version, result.source
```

Raw sklearn objects stay inside the eval package. Domain tool
`calculate_recovery_probability` calls this API and persists the score. It does
not execute recovery tools or change `amount_recovered`.

## Fallback

If the artifact is missing or unloadable, a deterministic simulator-rule score
is returned with `model_version=MODEL_FALLBACK` and `source=MODEL_FALLBACK`.

## Quality gates

Publish is refused when probabilities leave `[0, 1]`, metrics are NaN, ROC-AUC is below 0.60, PR-AUC is below 0.20, Brier is above 0.25, ECE is above 0.12, train/test case IDs overlap, leakage columns appear, or the test label is degenerate.

## Commands

```bash
uv run python -m recoverai_eval.train --seed 42 --n-cases 10000
uv run python -m recoverai_eval.evaluate --model-version recovery-v1
```

Equivalent without `PYTHONPATH`:

```bash
uv run python scripts/train_recovery_model.py --seed 42 --n-cases 10000
uv run python scripts/evaluate_recovery_model.py --model-version recovery-v1
```

No external API keys. Tests may use `--n-cases` well below 10k.

## Limitations

- Labels come from the local simulator, not production PSP outcomes.
- `ESCALATE` / `DO_NOTHING` are not payment-tool recoveries.
- Isotonic calibration needs a reasonably large validation set.
- The model does not rank actions or compute Expected Recovery Value. Phase 7
does that in `recoverai_domain.optimizer` using this inference API.

## Phase 8 handoff

Phase 8 should read `OptimizationResult` from Phase 7, then call
`ToolExecutionService`. Do not let the LLM calculate ERV or credit recovery.
